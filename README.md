# 核容锅筒工序扫码打卡原型

这是一个本地静态原型，用来说明“核容分厂锅筒从工艺路线导入、二维码打印、现场扫码完成打卡，到厂长看板同步”的完整业务闭环。

该目录不是生产系统代码，也不连接真实后端。所有上传、打印、扫码、看板同步都通过浏览器 `localStorage` 模拟。

## 推荐入口

直接打开：

```text
file:///Users/cdya/code/川锅/prototypes/drum-scan-checkin/index.html
```

`index.html` 是 SOP / 总入口页，适合先给业务、开发、实施同事统一讲清楚流程。

## 建议阅读顺序

开发同事第一次接手时，建议按这个顺序看：

1. 先打开 `index.html`，理解现场 SOP 和参与角色。
2. 再看 `upload.html`、`printer.html`、`checkin.html`、`dashboard.html` 四个独立页面分别模拟哪个真实系统。
3. 然后看 `assets/state.js`，理解 mock 数据、22 道工序、上传、打印、打卡、计划调整、打卡记录是怎么串起来的。
4. 最后看本 README 的“开发实现建议”和“验收点”，确认真实开发时哪些逻辑要落到后端。

这份原型的重点不是页面跳转，而是把“谁在什么系统里做什么动作、产生什么数据、影响哪个看板结果”讲清楚。

## 页面说明

| 页面 | 对应真实系统 | 使用人 | 说明 |
| --- | --- | --- | --- |
| `index.html` | SOP 总入口 | 所有人 | 说明整个业务流程、参与角色、现场规则、异常处理、系统入口。 |
| `sop.html` | SOP 备份入口 | 所有人 | 和 `index.html` 内容保持一致，保留直接访问旧 SOP 链接的能力。 |
| `upload.html` | 工艺路线数据源上传页 | 分厂技术员 / 班组长 | 上传令号对应的工艺路线表或压缩包，生成锅筒和工序数据。 |
| `dashboard.html` | 帷幄分厂管理看板 | 分厂厂长 / 调度 | 查看令号状态、锅筒工序进度、计划调整、打卡记录。 |
| `printer.html` | Android 热敏打印机应用 | 分厂技术员 / 打印责任人 | 选择令号并打印二维码标签。 |
| `checkin.html` | 手机扫码后的打卡页 | 各工序操作员 | 扫码后自动定位当前待完成工序，只点击“完成该工序”。 |

## 业务流程

1. 分厂技术员在 `upload.html` 上传工艺路线。
2. 厂长在 `dashboard.html` 看到该令号和锅筒工序计划。
3. 打印责任人在 `printer.html` 打印二维码标签。
4. 二维码贴到磁吸标签牌，挂到初始备料钢板上，并随工序流转。
5. 每道工序完成后，操作员用手机扫码进入 `checkin.html`。
6. 工人点击“完成该工序”，系统记录完成时间和打卡人。
7. `dashboard.html` 同步显示工序状态和打卡记录。

## 本地数据联动

所有页面共用：

```text
assets/state.js
STORAGE_KEY = cg_drum_scan_checkin_split_demo_v1
```

主要数据对象：

| 对象 | 说明 |
| --- | --- |
| `drums` | 锅筒对象列表。每个锅筒包含令号、项目、图号、工序任务、扫码记录。 |
| `tasks` | 工序任务列表。每道工序包含计划开始、计划完成、状态、实际完成时间、打卡人。 |
| `scanRecords` | 打卡记录。记录谁在什么时候完成了哪道工序。 |
| `printJobs` | 打印记录。记录二维码标签打印动作。 |
| `routeSource` | 最近一次上传的数据源信息。 |

注意：如果浏览器里已有旧的 `localStorage` 数据，页面会优先使用本地缓存。`state.js` 已做旧工序兼容迁移，会把旧的 `卷制/纵缝` 映射为 `纵缝`，并移除旧的 `完工` 工序。

如需从零演示，可以在浏览器控制台执行：

```js
localStorage.removeItem("cg_drum_scan_checkin_split_demo_v1");
location.reload();
```

## 已构造的演示数据

初始化时会自动构造多种状态的锅筒：

| 令号 | 状态 | 说明 |
| --- | --- | --- |
| `410503` | 在制 | 已完成前几道工序，有打卡记录。 |
| `1150053` | 待启动 | 工序尚未开始，暂无打卡记录。 |
| `32167-1` | 在制 | 中段工序进行中，有多条打卡记录。 |
| `3431` | 已完成 | 22 道工序全部完成。 |
| `410504` | 在制 | 后段工序进行中。 |

上传页新增令号后，会写入同一份本地状态，因此看板、打印页、扫码页都会读取到该令号。

## 关键需求规则

- 只打“完成卡”，不打“开始卡”。
- 对象粒度到锅筒，不再拆到核心组件级别。
- 二维码标签代表锅筒主对象，标签必须随实物流转。
- 工人扫码后页面自动定位当前待完成工序。
- 点击完成后会有短暂过渡，避免误点下一道工序。
- 厂长看板内可以查看打卡记录：工序、打卡人、完成时间。
- 计划调整只编辑锅筒主线工序的计划开始和计划完成日期。
- 上传重复令号时要提示数据覆盖风险，避免覆盖已打印二维码和已打卡记录。

## 开发实现建议

如果后续进入真实开发，不建议直接照搬静态代码结构。建议按真实系统边界拆分：

- 工艺路线上传页：独立数据源上传服务。
- 厂长看板：帷幄分厂管理中的功能模块。
- 打印页：Android 热敏打印机应用或移动 WebView。
- 扫码打卡页：手机端轻量 Web 页面。
- 后端接口：统一维护锅筒、工序计划、二维码、打卡记录。

建议后端至少提供这些接口能力：

| 能力 | 说明 |
| --- | --- |
| 导入工艺路线 | 根据令号生成锅筒和 22 道标准工序。 |
| 查询令号列表 | 按待启动、在制、已完成分组。 |
| 查询锅筒进度 | 返回工序计划、状态、最近打卡。 |
| 保存计划调整 | 保存每道工序的计划开始和计划完成日期。 |
| 生成二维码 | 按锅筒对象生成唯一二维码编码。 |
| 完成打卡 | 根据二维码定位当前待完成工序，并写入完成记录。 |
| 查询打卡记录 | 返回某个锅筒所有工序打卡流水。 |

## 验收点

开发同事拿到需求后，至少应满足：

- 打开总入口能理解完整业务流程。
- 上传一个令号后，看板能出现该令号。
- 打印页能选择该令号并打印二维码。
- 扫码页只显示完成动作，不出现开始打卡。
- 完成打卡后，看板当前工序推进到下一道。
- 看板能看到该锅筒的打卡记录。
- 工序名称与 22 道标准清单完全一致。
- 重复上传令号时有覆盖风险提示和处理策略。

## 线上部署

当前原型可以直接部署到 GitHub Pages。

仓库地址：

```text
https://github.com/cddadada/chuanguo
```

部署方式：

- 推送到 `main` 分支后，由 GitHub Pages 直接从分支发布静态文件。
- GitHub 仓库需要在 `Settings -> Pages` 中设置：`Deploy from a branch`、`Branch: main`、`Folder: /root`。
- 部署成功后，默认访问地址通常是：

```text
https://cddadada.github.io/chuanguo/
```

发布前确认：

- `index.html` 是默认入口。
- `assets/` 下的图片、视频、样式、脚本都已提交。
- 不要提交 `node_modules/`、`test-results/`、`.DS_Store`。
- 当前原型数据仍然是浏览器本地 `localStorage`，线上访问者之间不会共享同一份演示数据。
